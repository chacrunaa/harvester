# Инструкция 04 — Бизнес-функциональные требования (БФТ)

## Роль AI-агента

> Ты бизнес-аналитик и системный архитектор. Твоя задача — трансформировать потребности сегментов ЦА в конкретные функциональные требования к продукту, привязать их к компонентам системы и расставить приоритеты методами MoSCoW, ICE и RICE.

## Теоретическая база (из курса «Создание продуктовой концепции», модуль 2)

### Концепция продукта и требования

**Концепция продукта** — это система взглядов на будущий продукт, включающая:
- Для кого предназначается
- В чём ценность для пользователей
- Какое решение предлагается и чем оно отличается
- За счёт чего будет приносить прибыль

Фактически концепция продукта — это набор гипотез о будущем продукте. Каждое требование в БФТ — это проверяемая гипотеза.

### Продуктовый vs Проектный подход

| Критерий | Проектный подход | Продуктовый подход |
|---------|-----------------|-------------------|
| Основа | Фиксированное ТЗ | Потребности пользователей |
| Сроки | Заранее определены | Гибкие, меняются по данным |
| Главный риск | Продукт не соответствует рынку | Более редко |
| Работа с требованиями | Разовая | Итерационная |

**Lean-подход (бережная разработка):** создавать ценность, сокращая расходы на её производство. В рамках требований это означает: добавлять только то, что действительно нужно пользователям, проверенное данными.

### Методы приоритизации гипотез/требований

#### Метод Lean Prioritization (Эллен Готтесдайн)

Первичная сортировка по двум осям:
- **Value (Ценность)** — какой вклад приносит фича
- **Effort (Затраты)** — усилия на реализацию

```
                    HIGH VALUE
         ┌──────────────┬──────────────┐
HIGH     │  BIG BETS    │  QUICK WINS  │
EFFORT   │(крупные      │(быстрые      │
         │ставки) — #2  │победы) — #1  │
         ├──────────────┼──────────────┤
LOW      │  TIME SINKS  │  MAYBES      │
EFFORT   │(поглотители  │(возможности) │
         │ времени) — ∅ │ — #3         │
         └──────────────┴──────────────┘
                    LOW VALUE
```

**Очерёдность:** Quick Wins → Big Bets → Maybes. Time Sinks — не берём.

#### Метод ICE (Шон Эллис, автор Growth Hacking)

Оценка по трём критериям (шкала 1–10):

```
ICE Score = Impact × Confidence × Ease
```

| Критерий | Что означает | Оценка |
|---------|-------------|--------|
| **Impact** | Степень влияния на ключевой показатель | 1–10 |
| **Confidence** | Уверенность в оценках Impact и Ease | 1–10 |
| **Ease** | Лёгкость реализации (больше = легче) | 1–10 |

**Плюс:** быстро, наглядно. **Минус:** всего 3 параметра, субъективность.

#### Метод RICE (Sean Ellis + Morgan Brown, «Hacking Growth»)

Более сбалансированная версия ICE с добавлением охвата:

```
RICE Score = (Reach × Impact × Confidence) / Effort
```

| Критерий | Что означает | Как считать |
|---------|-------------|------------|
| **Reach** | Количество людей, которых коснётся идея | Конкретное число за период |
| **Impact** | Влияние на показатель | 3 = массовое; 2 = высокое; 1 = среднее; 0.5 = низкое; 0.25 = минимальное |
| **Confidence** | Уверенность в оценке (%) | 50%–100% (ниже 50% — не берём) |
| **Effort** | Трудозатраты | Человеко-недели для 1 специалиста |

**Пример RICE-расчёта:**

| Требование/Фича | Reach | Impact | Confidence | Effort | RICE Score |
|----------------|-------|--------|-----------|--------|-----------|
| Система достижений (геймификация) | 50 000 | 2 | 0.8 | 4 | 20 000 |
| AI-персонализация темпа | 50 000 | 3 | 0.7 | 8 | 13 125 |
| Напоминания и дедлайны | 50 000 | 1 | 0.9 | 2 | 22 500 |
| Социальные функции | 30 000 | 0.5 | 0.6 | 6 | 1 500 |

**Плюс:** точнее ICE, учитывает трудозатраты в человеко-неделях. **Минус:** уверенность субъективна.

> **Важно:** методы приоритизации — не окончательный приговор, а упражнение для измерения уровня уверенности команды.

| Компонент | Описание | Технологии (примерно) |

| Платёжная система | Обработка транзакций | ЮKassa, Stripe |
| CMS / Панель контента | Управление контентом | … |
| Дашборд аналитики | Метрики для команды | Amplitude, Metabase |

### 2. Таблица БФТ

Для каждой комбинации «сегмент + проблема» заполни строку:

| № | Сегмент | Проблема сегмента | Существующее решение (конкурент) | Минусы существующего | Предлагаемое решение | Компонент | Функциональные требования | NFR (Non-Functional Requirements) | Конечный результат для пользователя | Бизнес-эффект |
|---|---------|-------------------|----------------------------------|---------------------|---------------------|-----------|--------------------------|-----------------------------------|-------------------------------------|--------------|
| 1 | … | … | … | … | … | … | … | … | … | … |

**Пояснения к колонкам:**
- **Функциональные требования** — что система ДЕЛАЕТ: глаголы (отображать, сохранять, рассчитывать, уведомлять, персонализировать)
- **NFR** — как система работает: скорость (загрузка < 3 сек), надёжность (uptime 99.9%), безопасность (шифрование), доступность (WCAG 2.0)
- **Конечный результат** — что пользователь получает в результате использования функции
- **Бизнес-эффект** — рост retention, снижение CAC, увеличение CR, улучшение NPS

### 3. Приоритизация по MoSCoW

Для каждого требования из таблицы БФТ расставь приоритет:

| Приоритет | Определение | Критерий |
|-----------|------------|----------|
| **Must** | Критично для MVP | Без этого продукт не работает или не решает ключевую проблему |
| **Should** | Важно, но можно отложить | На v1.1, если MVP работает |
| **Could** | Желательно | В идеальном мире, при наличии ресурсов |
| **Won't** | Не в этой итерации | Явно исключаем, можно пересмотреть позже |

## Формат вывода

Markdown с полной таблицей БФТ + MoSCoW + ICE/RICE-скоринг. Каждое требование — отдельная строка.

## Фреймворки

- **MoSCoW** — Must / Should / Could / Won't — приоритизация требований
- **Lean Prioritization** (Эллен Готтесдайн) — Quick Wins / Big Bets / Maybes / Time Sinks
- **ICE Score** = Impact × Confidence × Ease (Шон Эллис)
- **RICE Score** = (Reach × Impact × Confidence) / Effort (Sean Ellis, Morgan Brown)
- **Дерево гипотез** — структура причинно-следственных связей
