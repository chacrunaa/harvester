# Архитектурные правила

Модульный монолит, bounded contexts: `auth`, `management`, `advertising`, `analytics`, `audit`, `notification`, `runtime`.
Разрешённый основной поток зависимостей: `handler → service → repository`.

## Container-first

- Для доменов используются контейнеры сервисов, репозиториев и outbound-клиентов.
- Новые зависимости добавляются в domain container, а не разбрасываются по init-файлам.
- Init-файлы не должны превращаться в место для междоменной бизнес-логики.

## Обязательный preflight перед реализацией

- Перед изменением структуры определить тип изменяемого кода: domain layer, generic infrastructure, transport integration, outbound client, job infrastructure.
- Перед рефакторингом найти уже существующий паттерн проекта для аналогичного слоя и встраиваться в него.
- Если в задаче есть TODO или эмоциональные формулировки, нельзя трактовать их как разрешение на свободный редизайн.
- Перед реализацией зафиксировать, какие слои будут затронуты: `constants`, `config/.env`, `dto`, `mapper`, `routes`, `docs`, `swagger`, контейнеры.
- Если задача неоднозначна, сначала сузить интерпретацию до минимально необходимой. Нельзя раскрывать объём задачи за счёт догадок.

## Правила против недопонимания

- Перед реализацией сверять смысл задачи с текущей предметной моделью и именованием. Если метод/роут работает с `user`, нельзя называть его `profile`, `info` или иначе семантически уже.
- Не придумывать новые сущности, поля, маршруты и миграции «на вырост», если этого нет в задаче или спецификации.
- Если задача ссылается на спецификацию в `docs/domains/**`, сначала сверять реализацию с ней.
- Если реализация требует архитектурного выбора, выбирать вариант, соответствующий уже существующей структуре проекта.

## Границы доменов и интеграции

- Один домен не имеет права обращаться к repository, service или entity другого домена напрямую.
- Междоменные операции выполняются только через outbound client или orchestration use case.
- Если данные логически принадлежат другому домену, они не дублируются в локальной entity без явного согласования.
- Генерация паролей, auth-провижининг и иная auth-логика не размещаются в `management`.
- Outbound-клиенты подключаются через контейнер домена. Нельзя протаскивать чужой сервис напрямую.

## Правила для outbound HTTP и jobs

- `internal/infrastructure/integration/outbound/http` — отдельный стандартизированный transport-слой. Нельзя перестраивать без опоры на уже существующую структуру.
- Нужно строго различать generic transport-механику и domain-specific реализацию поверх неё.
- Нельзя держать несколько конкурирующих реализаций для `request`, `response`, `errors`, `classify`, `validate`, `builder`, если они решают одну transport-задачу.
- `builder`, `process`, `validate`, `classify`, `errors` раскладываются по реальной ответственности слоя.
- В `internal/jobs` нужно разделять общую job-инфраструктуру и domain-specific job-логику.
- После любого структурного рефакторинга в `internal/jobs` или `outbound/http` проверять на наличие дублей пакетов и полумёртвых helper-файлов.

## Правила use case, роутов и handler-слоя

- Имена use case, handler-методов, DTO и роутов должны совпадать по смыслу. Если endpoint возвращает пользователя, это `GetUser`, а не `GetProfile`.
- Список маршрутов должен быть консистентным внутри ресурса.
- Если фича уже объединена под ресурсом `user`, не выделять альтернативный handler/module `userinfo` без чёткой архитектурной причины.
- Новые адаптеры называть по их реальной роли. Если компонент не является domain service, не держать его в service-пакете только «по месту».

## Транзакции и побочные эффекты

- Внешние побочные эффекты для другого домена нельзя запускать до commit без явно согласованной стратегии eventual consistency.
- Если междоменная операция выполняется после commit, нужно либо иметь компенсацию, либо явно зафиксированную допустимость частичного успеха.
- Не запускать фоновые sync/provision операции «по умолчанию», если их сбой оставляет систему в неоговоренном промежуточном состоянии.

## Правила для документации

- После изменения маршрутов, DTO, success/error payload или swagger-аннотаций нужно синхронизировать `docs/domains/**`.
- При изменении handler swagger-аннотаций нужно перегенерировать swagger через `make swagger`.
- Обзорные документы в `docs/index.md`, `docs/architecture/**`, `docs/shared/**` должны отражать только реально зарегистрированные маршруты.
