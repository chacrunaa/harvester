# Frontend Architecture Rules

> Правила ниже — **строгие**, если явно не помечено иначе.
> Нарушение строгого правила = архитектурная ошибка.
> Источники: `docs/structure/architecture.md`, `docs/structure/flexible-design.md`,
> `docs/structure/modules/`, `docs/structure/components/`.

---

## Строго запрещено

### Слои и границы

- **Модуль не импортирует JSX другого модуля.** `modules/A/` не может делать `import B from '@/modules/B/B'`. Обмен — через `query.ts`, `store.ts` или глобальный store.
- **Подмодуль не импортируется за пределами родительского модуля.** `modules/Chat/MessageList/` виден только `Chat.tsx`.
- **Подмодуль содержит только `.tsx` и `.module.scss`.** `entity.ts`, `query.ts`, `store.ts`, `services.ts` остаются на уровне модуля.
- **Страница не обращается к API и stores напрямую.** Только монтирует модули и задаёт layout.
- **Компонент из `components/` не вызывает `useQuery`, `useMutation`, не читает Zustand store.** Все данные — через пропсы.
- **Бизнес-логика и условия домена не живут в `components/`.** Это ответственность модуля.

### Состояние

- **WS бизнес-данные (сообщения, события) не попадают в `websocket.store`.** Там только статус соединения: `connecting | connected | disconnected | error`.
- **Глобальный Zustand store в `stores/` — только при реальной кросс-модульной необходимости.** Состояние одного модуля остаётся в его `store.ts`.

### Стилизация

- **Нельзя смешивать `*.module.scss` и MUI `sx`/`styled` на одном компоненте.** Один подход на компонент.
- **Нельзя смешивать MUI `theme.breakpoints` и SCSS-переменные в одном компоненте.** В `sx`/`styled` — MUI breakpoints, в `*.module.scss` — переменные из `variables.scss`.
- **В `*.module.scss` запрещён восходящий порядок breakpoints (`min-width`).** Только `max-width` в убывающем порядке.

### Компоненты

- **CSS-пропсы запрещены.** `marginBottom`, `width`, `color` — не пропсы компонента, это `sx`.
- **Boolean-флаги для визуальных вариантов запрещены.** Три boolean → один enum `variant`.
- **Строковые литералы в `queryKey` запрещены.** Только через константы: `chatKeys.detail(id)`, не `['chat', 'detail', id]` инлайн.

### Конфигурация

- **URL бэкенда не хардкодится нигде в коде.** Только `import.meta.env.VITE_API_URL` и `import.meta.env.VITE_WS_URL`.
- **`interface` только для module augmentation сторонних типов.** Везде — `type`.

## Избегать

- **Условный рендер разных «экранов» внутри одной страницы.** Если контент кардинально разный — нужны отдельные маршруты.
- **`if/else` по типу сообщения в JSX.** Использовать registry-паттерн в `services.ts`, где `MessageType → Component`.
- **Борьба с MUI-специфичностью.** Если MUI-компонент требует `!important` или `:global()` в 3+ местах — рассмотреть замену на нативный с `*.module.scss`.
- **`!important` без комментария.** Каждое использование сопровождается объяснением, почему другие способы не сработали.
- **Дублирование MUI-пропсов.** `isDisabled` вместо `disabled` — не создавать переименованные пропсы, если MUI уже их имеет.
- **Обёртка MUI-компонента при использовании в одном месте.** Обёртка оправдана при 3+ использованиях или необходимости стандартизировать пропсы.
- **Расширение существующего сабмодуля вместо создания нового.** Новый тип ввода (голос, файл) — новый сабмодуль, не раздутый `MessageInput`.
- **Глупый компонент читает store напрямую.** Если компоненту нужен store — он переезжает в `modules/`.

## Принятые соглашения

### Разделение ответственности по слоям

| Слой | Путь | Ответственность |
|---|---|---|
| Компоненты | `components/` | Глупые UI-примитивы. Только пропсы, никаких запросов и stores |
| Модули | `modules/` | Умные бизнес-единицы. API, stores, WS, бизнес-логика |
| Страницы | `pages/` | Маршрутный контейнер. Монтирует модули, задаёт layout |
| Layouts | `app/layouts/` | Скелет экрана, общий для нескольких страниц |

**Паттерн «умный родитель — глупый ребёнок»:** модуль читает store → передаёт данные в компонент через пропсы. Компонент не знает об источнике данных.

### Управление состоянием

| Тип | Инструмент |
|---|---|
| Данные с сервера, кэш, loading/error | TanStack Query (`query.ts` модуля) |
| UI-состояние одного модуля | Zustand (`modules/*/store.ts`) |
| Состояние нескольких модулей | Zustand (`stores/` глобальный) |
| Статус WS-соединения | `stores/websocket.store.ts` |
| Черновики форм в реальном времени | React Hook Form (uncontrolled) |

### WebSocket

Одно соединение на приложение. События тегированы идентификатором контекста (например, `chatId`). Модуль подписывается через хук и фильтрует только свои события:

```
websocketClient.ts     → connect/subscribe примитивы
websocket.store.ts     → статус соединения
Module/services.ts     → маппинг WS-события → доменная сущность
Module/hooks/useXxx.ts → React-хук: подписка + фильтрация
```

### Стилизация — уровни (применять в порядке)

1. `sx` prop — точечное, одноразовое переопределение MUI
2. `styled()` API — переиспользуемый вариант MUI-компонента
3. `*.module.scss` — кастомный компонент не на базе MUI
4. `:global(.MuiXxx)` в SCSS — таргетинг внутренних частей MUI из родителя
5. `ThemeProvider` override — глобальное изменение для всего приложения
6. `!important` — последний рубеж, с обязательным комментарием

### Формы

React Hook Form + Zod. Zod-схема — единственный источник типов формы, отдельные TypeScript-интерфейсы для форм не создаются. При WS-формах — `reset(wsMessage.data)` в `useEffect`.

### Адаптивность

Desktop-first. Базовые стили — 1280px+. Breakpoints по убыванию через `max-width`. Переменные из `app/styles/variables.scss`.

### Типизация

`type` везде. `interface` — только для module augmentation. Query-ключи — константы в `query.ts` каждого модуля.

### Подмодули

Появляются когда `ModuleName.tsx` становится слишком сложным. Структура плоская (все сабмодули на одном уровне). `store.ts` и `services.ts` остаются едиными на уровне модуля; подмодульный `services.ts` появляется только при значимой специфичной логике.

## К чему стремимся

**Предсказуемость по пути.** Путь файла однозначно говорит о его ответственности: `components/` — глупый, `modules/` — умный, `pages/` — маршрутный контейнер. Новый разработчик не должен угадывать, где искать логику.

**Изолированный рост.** Новый модуль добавляется без правки существующих. Новый тип сообщения — запись в registry, не правка `MessageList.tsx`. Новый провайдер — новая конфигурация, не новый JSX-блок.

**Глупые компоненты остаются глупыми.** Компонент из `components/` никогда не знает, откуда пришли данные. Это гарантирует переиспользование без побочных эффектов.

**Минимум абстракций.** Структура создаётся под реальную необходимость, не под гипотетический будущий сценарий. Три похожих случая — повод для абстракции, один — нет.

**Замена без страха.** Любой модуль можно заменить, не трогая других, при условии соблюдения публичного API через `index.ts`. Межмодульный обмен — только через `query.ts`, `store.ts`, глобальный store.

**WS не размазывается.** Все WS-данные живут в store модуля, который ими владеет. Глобальный `websocket.store` — только соединение. Это предотвращает неочевидные зависимости между несвязанными модулями.
