# Go-конвенции и структура файлов

## Структура файлов

- Публичные use case management user лежат в `internal/service/management/user/facade.go`. Не дублировать ответственность между `service.go` и `facade.go`.
- Приватные helper-функции service-слоя выносить в `helpers.go`, если они разрастаются.
- Mapper-файлы делить по фичам: `user.go`, `team.go`, `visibility.go`. Не собирать разнородный mapping в один файл.
- DTO-интеграции: `request.go` и `response.go`, если нет сильной причины иначе.
- Общие transport DTO (например общую пагинацию) выносить в общий пакет DTO, а не дублировать по фичам.
- Если по таблице уже есть основная entity, не создавать лишние почти одинаковые entity/params-структуры. Допустимы только специализированные фильтры и lightweight query params.
- Большие SQL-конструкции выносить из кода сборки логики в отдельные query-файлы/константы. В query-пакете не должно быть бизнес-логики.

## Качество реализации

- Не терять ошибки при промежуточных присваиваниях и не перезаписывать `err` до проверки.
- Названия ошибок, логов и event type должны соответствовать реальному действию: чтение не логируется как update, delete как create и т.д.
- Если в проекте уже есть константа или конфиг, переиспользовать его, а не создавать локальный дубль.
- Если значение влияет на retry/backoff, timeout, лимиты или внешний контракт, оно не должно оставаться в локальном хардкоде без явного основания.
- Generic-решение нельзя считать валидным только потому, что оно «похоже на переиспользуемое». Сначала проверить, действительно ли оно используется как общая механика.

## API-контракт

Ответ: `{success: bool, data: T, error: {code, message}}`.
