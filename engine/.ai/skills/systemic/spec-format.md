# Формат системной спецификации

Инструкция для `owner` и `analyst`. Определяет структуру spec.md —
главного технического документа pipeline, который читают backend, frontend, qa, penetration.

---

## Назначение spec.md

spec.md — единственный источник истины для фазы разработки.
Разработчики реализуют только то, что описано в spec.
QA проверяет только acceptance criteria из spec.

---

## Структура spec.md

### 1. Заголовок

```markdown
# Спецификация — {task-id}: {Название продукта}

**Версия:** {дата}
**Стек:** {язык} + {фреймворк} + {БД} + {другое}
**Тип:** {personal tool / SaaS / mobile / etc.}
```

### 2. Обзор системы

Краткое описание что строим (2–3 предложения). Что система делает и для кого.

### 3. Архитектура

Компоненты системы и их взаимодействие:

```
[Frontend] → [API] → [Backend Service] → [Database]
                ↓
         [External Services]
```

Описание каждого компонента: назначение, технология, порт.

### 4. Схема базы данных

Для каждой таблицы:

```sql
CREATE TABLE {table_name} (
  id          SERIAL PRIMARY KEY,
  {field}     {type} {constraints},
  created_at  TIMESTAMP DEFAULT NOW()
);
```

Индексы, внешние ключи, constraints — явно.

### 5. API Endpoints

Для каждого endpoint:

```
{METHOD} {/path}
Auth: {required / none}
Request: {body schema или params}
Response 200: {schema}
Response 4xx: {error cases}
```

### 6. Acceptance Criteria

Пронумерованный список проверяемых условий:

```
AC-01: {конкретное, проверяемое условие}
AC-02: …
```

Критерии: формулировка «Given … When … Then …» или «Система должна [глагол] [объект]».
Не использовать: «работает корректно», «отображает правильно».

### 7. Нефункциональные требования

- Производительность: время отклика < X мс при N RPS
- Безопасность: JWT / bcrypt / HTTPS / что конкретно
- Доступность: платформы, браузеры

### 8. Out of scope

Что явно НЕ реализуется в этой версии. Снимает двусмысленность.

---

## Правила написания spec

- Каждый AC — отдельный, независимо проверяемый критерий
- Схема БД — полная, с типами и constraints, без «и т.д.»
- API — каждый endpoint с примером request/response
- Если что-то неясно — лучше задать вопрос, чем придумать
- Out of scope обязателен — без него QA будет тестировать лишнее
