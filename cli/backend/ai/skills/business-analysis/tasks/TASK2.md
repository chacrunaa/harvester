# TASK2 — Анализ ответов и итеративный сбор дополняющих документов

## Цель

После получения ответов на вопросы по проекту нужно собрать и структурировать дополнительную информацию, чтобы дополнить исходные материалы из `data/input/`. Этот процесс **итеративный**: он повторяется столько раз, сколько нужно — пока все критичные пробелы не будут закрыты.

## Алгоритм работы (обязательно соблюдать)

```
ШАГ A: Изучи все файлы из data/input/ и data/info/
         ↓
ШАГ B: Составь список критичных пробелов (без чего нельзя делать следующие шаги)
         ↓
ШАГ C: Если пробелы есть → сформируй вопросы → сохрани в questions/ → жди ответов
         ↓
ШАГ D: Получи ответы клиента → структурируй их → сохрани в data/info/
         ↓
ШАГ E: Снова оцени: все ли критичные пробелы закрыты?
         ↓ НЕТ                              ↓ ДА
      Вернись на ШАГ C              Переходи к TASK3
```

**Количество итераций:** от 0 до бесконечности. Если входные данные полные — итераций 0. Если данных мало — может быть 10–20 раундов вопросов. Задача всегда одна: не переходить к TASK3, пока есть критичные незакрытые пробелы.

## Критичные пробелы (примеры того, без чего нельзя продолжать)

- Неизвестна целевая география и горизонт планирования
- Не определены приоритетные сегменты ЦА для MVP
- Нет никакого представления о ценообразовании
- Нет целевых KPI (хотя бы в виде диапазонов)
- Нет понимания структуры расходов (хотя бы укрупнённо)
- Нет списка конкурентов (хотя бы 1–3 названия)

## Что нужно сделать в каждой итерации

1. Изучить текущее состояние материалов (`data/input/` + `data/info/`).
2. Определить: каких данных не хватает для качественного бизнес-анализа.
3. Сформулировать **только критичные** вопросы (не задавать вопросы, если ответ уже есть в материалах).
4. Сохранить вопросы в `questions/ГГГГ-ММ-ДД-[тема].txt`.
5. **Одновременно** создать задание `tasks/TASK2q/q1.md` (или `q2.md` при следующей итерации) — описывает что именно обновить в `data/output/00-business-context.md` после получения ответов. Формат и пример: [`tasks/TASK2q/readme.md`](TASK2q/readme.md)
6. Дождаться ответов клиента.
7. Структурировать ответы и сохранить в `data/info/ГГГГ-ММ-ДД-[тема]-analysis.md`.
8. Снова оценить полноту данных → решить: продолжать итерации или переходить к TASK3.

## Правила формирования вопросов

- Не задавать вопрос, если ответ уже явно есть во входных материалах.
- Группировать по темам (ЦА, ценообразование, рынок, финансы, конкуренты).
- Формулировать так, чтобы ответ сразу можно было использовать в расчётах.
- В каждом вопросе объяснять, для чего он нужен (одна строка).
- Не раздувать список: лучше 5 точных вопросов, чем 20 размытых.

## Правила структурирования ответов

- Структурировать информацию так, чтобы её было удобно использовать как контекст для TASK3.
- Явно отмечать противоречия в ответах клиента.
- Явно разделять: факты (клиент подтвердил) vs гипотезы (клиент не знает / оценка предположительная).
- Новые документы должны дополнять `data/input/`, а не дублировать без необходимости.

## Критерии перехода к TASK3

Переходить к TASK3 можно только если выполнены **все** условия:
- [ ] Зафиксирована целевая география и горизонт планирования
- [ ] Определены 1–3 приоритетных ICP-сегмента для MVP
- [ ] Есть хотя бы примерная ценовая сетка (диапазон + 1–2 конкретных примера)
- [ ] Есть целевые KPI на 6 и 12 месяцев
- [ ] Есть понимание структуры расходов (пусть и укрупнённо)
- [ ] Есть хотя бы 1–3 названных конкурента
- [ ] Все выявленные критичные вопросы либо закрыты, либо явно помечены как «данных нет, используем гипотезу»

## Результат

- В `data/info/` есть структурированные материалы по всем критичным темам.
- Материалы расширяют и уточняют `data/input/`.
- Все критичные пробелы закрыты или явно помечены как гипотезы с обоснованием.
- Создан итоговый сводный документ `data/output/00-business-context.md` (см. ниже).

## Итоговый документ — сводка понимания бизнеса

**Перед переходом к TASK3 создать файл:** `data/output/00-business-context.md`

Этот документ — единый «паспорт проекта» для AI-агента: всё ключевое понимание бизнеса в одном месте, чтобы не читать десятки файлов из `data/input/`, `data/info/` и `questions/` перед каждым шагом TASK3.

### Структура `00-business-context.md`

**Раздел 1 — Суть продукта (3–5 предложений)**
Что это, для кого, какую проблему решает, как работает. Написать так, чтобы человек без контекста понял суть за 30 секунд.

**Раздел 2 — Факты о бизнесе (таблица)**

| Параметр | Значение | Источник |
|---------|---------|---------|
| Название продукта | | data/input/ |
| Тип бизнеса (B2C/B2B/B2B2C) | | data/input/ |
| Целевая география | | data/info/ |
| Горизонт планирования | | data/info/ |
| ICP-1 (приоритетный сегмент) | [название + краткое описание] | data/info/ |
| ICP-2 (приоритетный сегмент) | | data/info/ |
| Базовая цена | | data/info/ |
| Upsell-опция и цена | | data/info/ |
| Attach-rate upsell | | data/info/ |
| Конверсия visit→signup | | data/info/ |
| Конверсия signup→payment | | data/info/ |
| ФОТ команды | | data/info/ |
| Дата пилота | | data/info/ |
| Дата MVP | | data/info/ |
| KPI 6 мес (платящих / MRR) | | data/info/ |
| KPI 12 мес (платящих / MRR) | | data/info/ |

**Раздел 3 — Конкуренты (таблица)**

| Конкурент | Категория | Цена | Ключевое отличие |
|---------|---------|:----:|-----|
| [Конкурент из data/info/] | | | |

**Раздел 4 — Критичные зависимости и риски**

Перечень всего, без чего продукт не работает или что блокирует запуск. Брать из `data/info/`.

**Раздел 5 — Открытые вопросы и гипотезы**

Что неизвестно на момент начала TASK3 — явно перечислить с пометкой `[гипотеза]`. Это поможет агенту понять, где нужно ставить `[гипотеза]` в расчётах.

**Раздел 6 — Что уточнили через questions/**

Краткий список: какие вопросы задавались, какие ответы получены, что это изменило в понимании бизнеса.

### Требования к документу

- Минимум 80–120 строк
- Все таблицы заполнены реальными данными (нет пустых ячеек)
- Нет пересказа — только структурированные факты и числа
- После создания этого документа — приступать к TASK3
