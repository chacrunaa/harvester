### 7. Метрики валидации MVP (пороги успеха)

Значения определить из `data/info/` и логики продукта:

| Метрика | Порог «провал» | Порог «ок» | Порог «успех» | Срок измерения |
|---------|---------------|-----------|--------------|----------------|
| Заказов за M1 | < (N) | (N–M) | ≥ (M) | Конец M1 |
| signup→payment CR | < (из data/info()) | (диапазон) | ≥ (из data/info/) | M1–M3 |
| NPS | < 20 | 20–39 | ≥ (из data/info/) | M3 |
| D3 Retention | < (порог) | (диапазон) | ≥ (из data/info/) | M2–M3 |
| Time-to-value | > (максимум) | (диапазон) | < (цель) | M1 |
| Upsell attach-rate | < (порог) | (диапазон) | ≥ (из data/info/) | M2 |

Действия по итогам:
- «Провал» по 3+ метрикам → переосмыслить продукт
- «Ок» по всем → продолжить, улучшить узкие места
- «Успех» по 4+ → масштабировать

## Требования к качеству

- User Journey — минимум 10 шагов с заполненными всеми колонками
- Must-Have функции — минимум 8 строк, взятых из BFT
- Гипотезы — минимум 7 с конкретными критериями подтверждения
- Метрики валидации — 3 уровня (провал/ок/успех) для минимум 6 метрик
- Roadmap — 5 версий с датами или квартальными горизонтами

## Что НЕ делать

- Не придумывать функции MVP — брать только из `data/output/04-bft/` (Must-категория)
- Не ставить критерий «успех» без числового порога
- Не писать «позже» в roadmap — конкретный квартал/месяц
- Не забывать GTM-план — без него MVP никто не увидит
- Не пропускать сравнение фаз (Пилот vs MVP) — это ключевая особенность проекта
