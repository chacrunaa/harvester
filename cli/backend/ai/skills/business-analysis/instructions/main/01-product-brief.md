# Инструкция 01 — Product Brief (Описание продукта)

## Выходные файлы

**Главный файл:** `data/output/01-product-brief/01-product-brief.md`

Если какой-либо раздел (фазы, гипотезы) занимает много места — создай дополнительные файлы в той же папке.
Количество файлов определяешь сам исходя из объёма содержания.

**НЕ создавай README.md — это заглушка, не результат.**

---

## Роль

Ты — продакт-менеджер, который пишет документ для команды, инвесторов и себя.
Не заполняй шаблон. Думай как человек, который создаёт этот продукт и хочет объяснить его суть так,
чтобы любой читатель сразу понял: что это, для кого, зачем, как работает, какие деньги и риски.
Этот документ — фундамент для всех остальных шагов анализа.

---

## Входные файлы — прочитать ВСЕ перед написанием

1. `data/input/intro.md` — суть продукта, проблема, решение, фазы
2. `data/input/business/overview.md` — бизнес-контекст
3. `data/input/business/business-model.md` — монетизация
4. `data/input/business/competitive-analysis.md` — конкуренты (если есть)
5. `data/input/features/` — все файлы функциональности
6. `data/input/architecture/` — фазы разработки и технический стек
7. `data/info/` — все файлы с данными клиента: конверсии, KPI, ценообразование, риски, пробелы
8. `questions/` — уточняющие вопросы и ответы, если есть

## Раздел 1 — Аннотация

**Что это:** Одно предложение, которое исчерпывающе описывает продукт. Человек должен понять суть с первого прочтения.

**Как писать:**
1. Из `data/input/intro.md` выпиши: название продукта, что именно делает (глагол + объект), для кого.
2. Из `data/info/` выпиши: главное преимущество перед конкурентами, ключевую выгоду для пользователя.
3. Из `data/input/intro.md` или `data/input/business/competitive-analysis.md` выпиши главную боль: сколько стоят или насколько неудобны текущие решения.
4. Составь одно предложение по формуле:
   «[Название] — это [категория продукта], который [конкретное действие + измеримая выгода или скорость] для [ЦА из данных], позволяющий [результат] без [главной боли с конкретикой из данных].»

**Пример формата (не копировать — составить с данными проекта):**
> «[Продукт] — это [тип сервиса], который за [время/количество шагов] [делает что именно] для [кто это], позволяя [конкретный измеримый результат] без [текущей боли с цифрой стоимости или времени].»

## Раздел 2 — Product Vision Statement

**Что это:** Шаблон из 6 строк, который точно формулирует для кого продукт, какую проблему решает и чем отличается. Заполняется полностью — без пустых строк.

**Как писать каждую строку:**
1. **Для:** — конкретная ЦА из `data/info/`. Не «широкая аудитория», а сегмент с характеристикой.
2. **Кому нужно:** — конкретная проблема/потребность из `data/input/intro.md`. Что они хотят сделать или перестать делать.
3. **[Название продукта] — это:** — категория продукта одной короткой фразой.
4. **Который:** — главное преимущество с конкретной цифрой или фактом из данных (скорость, цена, охват, точность).
5. **В отличие от:** — перечисли реальных конкурентов из `data/info/` и `data/input/business/competitive-analysis.md` по имени.
6. **Мы:** — принципиальное отличие от всех перечисленных конкурентов. Одна фраза, конкретно.

**Результат — 6 заполненных строк без скобок и без «(из данных)»:**
```
Для: [конкретный сегмент из data/info/]
Кому нужно: [конкретная задача/проблема из данных]
[Название] — это: [категория]
Который: [преимущество с числом или фактом]
В отличие от: [конкуренты по имени из данных]
Мы: [принципиальное отличие]
```

## Раздел 3 — Описание продукта

**Что это:** Паспорт продукта — таблица с основными характеристиками. Должна давать полное понимание контекста за 30 секунд.

**Как писать:**
1. Прочитай `data/input/intro.md` — выпиши все факты: название, категория, как работает, рынок, охват.
2. Прочитай `data/input/architecture/` — добавь: технический стек, даты фаз.
3. Прочитай `data/info/` — добавь: целевую географию, горизонт планирования, размер команды.
4. Заполни таблицу только реальными данными. Минимум 10 строк.

**Таблица — заполнить каждую ячейку (без «(из данных)», только реальные значения):**

| Параметр | Значение |
|---------|---------|
| Полное название | (из data/input/) |
| Категория | (конкретно — тип сервиса, рынок) |
| Рынок | (B2B / B2C / B2B2C, из данных) |
| Стадия | (из данных: дизайн / разработка / запуск) |
| Целевая география | (из data/info/) |
| Охват | (страны / категории / вертикали, из данных) |
| Горизонт планирования | (из data/info/) |
| Дата пилота | (из data/info/ или data/input/architecture/) |
| Дата MVP / публичного запуска | (из данных) |
| Команда | (состав и условия из data/info/) |
| ... | (другие параметры из данных) |

## Раздел 4 — Проблема и контекст

**Что это:** Обоснование того, почему продукт существует. Без чёткого описания проблемы невозможно оценить ценность решения.

**Как писать:**
1. Прочитай `data/input/intro.md` раздел «Проблема» — выпиши все перечисленные проблемы.
2. Для каждой проблемы определи: насколько острая (1–5), используй логику — если блокирует ключевое действие пользователя или стоит значительных денег/времени — острая (4–5).
3. «Как решают сейчас» — конкретно: какие альтернативы используют (конкуренты, ручные процессы, другие продукты).
4. «Стоимость текущего решения» — деньги или время из `data/input/` и `data/input/business/competitive-analysis.md`.
5. После таблицы напиши 2–3 абзаца: почему именно сейчас подходящее время (тренды, рост сегмента, изменения рынка).

**Таблица — заполнить каждую ячейку (минимум 4 проблемы):**

| Проблема | Острота (1–5) | Как решают сейчас | Стоимость текущего решения |
|---------|:---:|-----|------|
| (из data/input/intro.md) | (обоснуй логически) | (конкретная альтернатива) | (деньги или время) |
| ... | | | |

## Раздел 5 — Решение (модули продукта)

**Что это:** Описание конкретной функциональности продукта — не концепция, а реальные возможности.

**Как писать:**
1. Прочитай все файлы из `data/input/features/` — выпиши все модули.
2. Для каждого модуля напиши: что делает технически (1 предложение, глагол + объект) + какую ценность создаёт для пользователя (1 предложение с конкретикой).
3. Напиши вводный абзац перед таблицей: как модули связаны в общий пользовательский путь.

**Таблица — по одному модулю на каждый файл из data/input/features/ (минимум 5):**

| Модуль | Что делает | Ценность для пользователя |
|--------|-----------|--------------------------|
| (из data/input/features/) | (конкретно что происходит) | (что получает пользователь, без абстракций) |
| ... | | |

## Раздел 6 — Product Vision Board

**Что это:** Стратегический документ на одной странице — для кого, зачем, что предлагает, какие цели.

**Как писать каждый блок:**

**Vision** (3–5 предложений):
1. Из `data/input/intro.md` — что изменится в жизни пользователей с появлением продукта.
2. Формулируй через конкретику: «вместо X часов на Y — Z минут», «вместо W <currency> — V <currency>».
3. Не писать «изменим мир» — писать что конкретно изменится для конкретного человека.

**Target Group**:
1. Из `data/info/` — возьми все ICP-сегменты с приоритетами.
2. Для каждого — краткий профиль: кто это, их ситуация, почему им нужен продукт.

**Needs** (топ-3 потребности для каждого сегмента):
1. Из `data/output/02-target-audience/` (если уже выполнен) или из `data/info/`.
2. Для каждого сегмента — минимум 3 конкретные потребности.

**Product** (ключевые функции, минимум 6):
Перечисли все модули из раздела 5.

**Business Goals** (только из `data/info/`):
Возьми KPI на 6 и 12 мес — конкретные числа: платящие пользователи, MRR, retention, NPS.

**Таблица — заполнить каждую ячейку, без пустых строк:**

| Блок | Содержание |
|------|-----------|
| **Vision** | [3–5 предложений с конкретными числами из данных] |
| **Target Group** | [Сегменты из data/info/ с кратким профилем] |
| **Needs** | [≥3 потребности для каждого сегмента] |
| **Product** | [≥6 функций из data/input/features/] |
| **Business Goals** | [KPI из data/info/ — конкретные числа] |

## Раздел 7 — Ключевые метрики успеха

**Что это:** Таблица измеримых критериев, по которым команда будет понимать — движемся ли к цели.

**Как писать:**
1. Открой `data/info/` — выпиши ВСЕ числовые KPI: платящие пользователи, MRR, retention, NPS, конверсии воронки.
2. Для каждой метрики добавь промежуточную цель на 6 мес (логически — ~30–50% от цели 12 мес, если нет данных).
3. Добавь конверсионные метрики из данных клиента: visit→signup, signup→payment, attach-rate upsell.
4. Для каждой метрики укажи: что измеряет + источник данных (аналитика / CRM / платёжная система / опрос).

**Таблица — все KPI из data/info/ + логически выведенные промежуточные:**

| Метрика | Что измеряет | Цель 6 мес | Цель 12 мес | Источник |
|---------|------------|:----------:|:-----------:|---------|
| (KPI из data/info/) | (что именно измеряет) | (из данных или логическая экстраполяция) | (из data/info/) | (инструмент) |
| Конверсия visit→signup | Эффективность лендинга | (из data/info/) | (из data/info/) | Analytics |
| Конверсия signup→payment | Качество UX и ценность | (из data/info/) | (из data/info/) | Analytics |

## Раздел 8 — Ключевые гипотезы на старте

**Что это:** Неподтверждённые допущения, от которых зависит успех продукта. Не пожелания — конкретные утверждения с измеримыми критериями.

**Как писать:**
1. Открой `data/info/` — найди разделы «Пробелы» и «Риски/противоречия». Каждый пробел = гипотеза.
2. Открой `questions/` — незакрытые вопросы тоже превращаются в гипотезы.
3. Типы гипотез: о поведении пользователей, о рынке/спросе, о монетизации, о продукте, об операционной модели.
4. Для каждой гипотезы определи: измеримый критерий подтверждения (число, процент), метод проверки (CustDev / аналитика / A/B тест / данные после запуска).

**Таблица — минимум 7 гипотез, каждая строка полностью заполнена:**

| # | Гипотеза | Тип | Критерий подтверждения | Метод проверки |
|:--|---------|:---:|----------------------|----------------|
| H1 | Целевой сегмент готов платить [цена из данных] за [ценность продукта] | Монетизация | ≥[N]% оплачивают в первые [X] мес | Аналитика checkout |
| H2 | [Канал привлечения из данных] достаточен для достижения KPI | Привлечение | [KPI из data/info/] достигнут без платного CAC | Аналитика источников |
| ... | | | | |

## Раздел 9 — Конкурентное отличие

**Что это:** Таблица сравнения продукта с конкурентами по критериям выбора ЦА.

**Как писать:**
1. Из `data/input/business/competitive-analysis.md` и `data/info/` — выпиши всех конкурентов по имени.
2. Определи критерии сравнения исходя из болей ЦА (раздел 4): цена, скорость, охват, удобство, надёжность.
3. Для каждого конкурента оцени каждый критерий. Где нет данных — пиши `[оценка]` с логическим обоснованием.
4. Минимум 5 конкурентов (включая «Самостоятельно»). Минимум 7 критериев.

**Таблица — первый столбец — анализируемый продукт, затем конкуренты:**

| Критерий | [Продукт] | [Конкурент 1] | [Конкурент 2] | ... | Самостоятельно |

| Скорость | (из данных) | (оценить) | (оценить) | | (оценить) |

## Раздел 10 — Фазы разработки

**Что это:** Технический и продуктовый план — что строится когда и зачем.

**Как писать:**
1. Прочитай `data/input/architecture/pilot.md` — выпиши: цель пилота, стек, что исключено.
2. Прочитай `data/input/architecture/mvp.md` — выпиши: цель MVP, стек, что добавляется по сравнению с пилотом.
3. Для каждой фазы: дата (из `data/info/`), цель фазы одним предложением, технический стек конкретно, что явно исключено.
4. Добавь v1.0 и v2.0 с пометкой `[гипотеза]` — что будет добавлено после MVP на основе логики продукта.

**Формат каждой фазы:**

**[Название фазы] — [Дата из данных]**
- Цель: [одно предложение — что проверяем или достигаем]
- Стек: [конкретно из data/input/architecture/]
- Исключено: [что явно не входит в эту фазу]
- Отличие от предыдущей: [что добавляется]

## Раздел 11 — Ограничения, риски и допущения

**Что это:** Честный список всего, что может пойти не так или что неизвестно. Без этого — маркетинг, не анализ.

**Как писать:**
1. Из `data/info/` — раздел «Пробелы» и «Критичные зависимости» — это и есть ограничения.
2. Из `data/input/` — технические зависимости (платёжные системы, сторонние сервисы, провайдеры).
3. Из логики продукта — что вы ещё не знаете про спрос, цену, операционную модель.
4. Тип риска: рыночный / технический / операционный / финансовый / командный.
5. Влияние: В — высокое (блокирует бизнес), С — среднее (влияет на метрики), Н — низкое.
6. Митигация — конкретный ответ, не «мониторинг».

**Таблица — минимум 7 строк, каждая заполнена полностью:**

| Тип | Описание | Влияние | Митигация |
|-----|---------|:-------:|-----------|
| Рыночный | Нет подтверждённого спроса (CustDev не проводился) | В | Провести CustDev до запуска — план в шаге 12 |
| Технический | Зависимость от [сервис из data/info/] — если недоступен, [последствие] | В | [Конкретная митигация] |
| ... | | | |

## Требования к качеству документа

- Документ ≥ 150 строк markdown
- Каждая таблица заполнена — нет пустых ячеек, нет «(из данных)» без реального значения
- Все числа — из входных файлов или помечены `[гипотеза]` с обоснованием
- Конкуренты названы по именам из данных
- KPI раздела 7 совпадают с данными клиента из `data/info/`
- Гипотезы раздела 8 с измеримыми критериями, не абстрактные
- Фазы разработки с конкретными датами и стеком из архитектурных файлов

## Что НЕ делать

- Не оставлять ячейки таблиц с «(из данных)» — только реальные значения
- Не писать «высокий спрос» без числового обоснования
- Не пропускать ни один из 11 разделов
- Не придумывать конкурентов — только те, что есть в данных проекта
- Не придумывать цифры — всё из входных данных или `[гипотеза]` с обоснованием
