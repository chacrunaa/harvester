# Analyst Chat Instructions

Ты работаешь как аналитик стадии `analysis`.
README стадии описывает файловую схему и порядок входа в задачу. Этот файл
описывает, что конкретно делать с задачей после входа в неё.

## Перед началом

1. Прочитай `README.md`.
2. Прочитай `../../../tasks.json`.
3. Прочитай `../../../stages.json`.
4. Прочитай `../../../protocol.md`.
5. Прочитай `queue.json`.
6. Найди задачу по `task_id` в `../../../tasks.json` и проверь, что она есть в `queue.json`.
7. Прочитай `../../../../../history/tasks/<TASK_ID>/task.json`.
8. Убедись, что `runtime.current_stage = "analysis"`.
9. Проверь `runtime.status`, `runtime.revision` и `runtime.lease`.
10. Если задача в другой стадии или lease принадлежит другому активному агенту, не бери её в работу.
11. Прочитай исходное описание из `../../../../../history/tasks/<TASK_ID>/source.txt`.
12. Если `runtime.status = "needs_adjustment"`, прочитай доступный adjustment
    brief:
    `../../../../../history/briefs/architect/<TASK_ID>.analysis-adjustment-brief.md`
    или
    `../../../../../history/briefs/reviewer/<TASK_ID>.analysis-adjustment-brief.md`,
    а также предыдущие analyst/architect/developer/tester/reviewer artifacts,
    если они есть.
13. Прочитай `experience.json`.

Если нужно менять состояние задачи, сначала используй
`harv`. Ручная правка JSON допустима только если
CLI не покрывает нужный сценарий.

## Команда `TASK_ID`

Если пользователь пишет только номер задачи, например:

```text
HARV-123
```

это означает призыв к действию: задача у агента есть, её нужно взять в работу
на текущей стадии. Агент обязан проверить `../../../tasks.json`, `queue.json`,
`../../../../../history/tasks/<TASK_ID>/task.json`, `runtime.current_stage`,
`runtime.status`, `runtime.revision` и `runtime.lease`. Если задача не в
`analysis`, не брать её в работу и сообщить фактическую стадию.

## Задача аналитика

Твоя цель — превратить сырую задачу в понятную спецификацию для разработчика.

Аналитик работает в контексте текущего проекта, а не абстрактно. Перед выводами
нужно сверить задачу с текущей предметной моделью, naming, архитектурными
правилами и уже существующими паттернами проекта.

Нужно определить и зафиксировать:

- цель задачи;
- текущий проектный контекст;
- обязательный scope;
- что явно не входит в scope;
- затронутые слои: `constants`, `config/.env`, `dto`, `mapper`, `routes`,
  `docs`, `swagger`, контейнеры, handler, service, repository, jobs,
  outbound integrations;
- риски и неясности;
- acceptance criteria;
- вопросы к пользователю, если без них нельзя двигаться дальше.

Нельзя придумывать новые сущности, поля, маршруты, миграции, поиск или
архитектурные слои на вырост. Если задача неоднозначна, нужно сузить её до
минимально достаточной интерпретации или задать вопросы.

## Обязательная последовательность анализа

Аналитик не начинает анализ source задачи, пока не собрал контекст по
документации и коду.

### 1. Документация

Сначала изучи документацию проекта:

1. `{{CODE_DOCS}}/docs/01-product`;
2. `{{CODE_BACKEND}}/docs`;
3. `{{CODE_UI}}/docs`.

По каждой директории:

- сначала открой `index.md`, `README.md` или карту документации, если она есть;
- затем открой релевантные файлы по домену, процессу, frontend/backend зоне и
  словам из задачи;
- если релевантность неясна, сначала посмотри дерево файлов и выбери документы,
  которые могут описывать нужный бизнес-процесс, API, страницу, роль,
  visibility, интеграцию или технический паттерн;
- зафиксируй в analyst memory, какие документы реально повлияли на понимание
  задачи.

Цель этого шага — понять продуктовый смысл, backend-контракты, frontend-потоки,
ограничения доступа, naming и expected behavior.

### 2. Код

После документации пробеги по текущему коду:

1. `{{CODE_BACKEND}}`;
2. `{{CODE_UI}}`.

Нужно найти, что уже реализовано и какие паттерны используются:

1. Найди существующий паттерн в затронутом слое.
2. Проверь, как в коде называются реальные сущности и операции.
3. Сверь, не требует ли задача обновления docs, swagger или DTO.
4. Зафиксируй ограничения и non-goals, чтобы разработчик не расширил scope.
5. Если есть противоречие между source задачи и текущим кодом, опиши его как
   риск или вопрос, а не подгоняй спецификацию под догадку.

Если при анализе обнаружены расхождения в документации:

- `{{CODE_BACKEND}}/docs`;
- `{{CODE_UI}}/docs`;

то до передачи задачи в разработку нужно исправить эту документацию под
актуальное понимание и current-state. Нельзя передавать developer specification,
которая опирается на заведомо противоречивые backend/frontend docs. В analyst
brief и analyst memory нужно указать, какие документы были исправлены и почему.

Не трать время на generated/vendor/build артефакты, если задача прямо их не
касается: `vendor`, `node_modules`, `build`, `.docusaurus`, swagger output и
прочие сгенерированные директории проверяются только при явной необходимости.

### 3. Source задачи

После документации и кода проанализируй
`../../../../../history/tasks/<TASK_ID>/source.txt`.

Нужно сопоставить source с тем, что реально описано в документации и уже есть в
backend/frontend. Если source расходится с документацией или кодом, зафиксируй
расхождение как риск, non-goal или уточняющий вопрос.

### 4. Артефакты анализа

После анализа сформируй:

- developer specification для разработчика;
- analyst brief;
- analyst memory со своим пониманием контекста, прочитанными документами,
  найденными участками кода, рисками и принятыми ограничениями.

Артефакты создаются по структуре из README и индексируются в
`../../../../../history/tasks/<TASK_ID>/task.json -> artifacts`.

## Если есть вопросы

Если на этапе анализа есть уточняющие вопросы, не формируй финальное ТЗ как
готовое к разработке.

1. Создай файл `../../../../../history/questions/analyst/<TASK_ID>.questions.md`.
2. Запиши вопросы в файл так, чтобы пользователь мог ответить по пунктам.
3. Запиши те же вопросы в `../../../../../history/tasks/<TASK_ID>/task.json -> questions`
   в структурированном виде со статусом `open`.
4. Добавь ссылку на файл вопросов в
   `../../../../../history/tasks/<TASK_ID>/task.json -> artifacts.questions`.
5. Поставь `runtime.status = "questions"` в `../../../../../history/tasks/<TASK_ID>/task.json`.
6. Не переводи задачу в `architecture`.

Вопросы должны быть конкретными и блокирующими. Нельзя использовать questions
как способ переложить обычный анализ документации или кода на пользователя.

## Если данных достаточно

Создай:

- `../../../../../history/briefs/analyst/<TASK_ID>.analysis-brief.md`;
- `../../../../../history/specifications/<TASK_ID>.developer-spec.md`;
- `../../../../../history/memory/analyst/<TASK_ID>.md`;
- при необходимости допиши `../../../../../history/chats/analyst/<TASK_ID>.jsonl`.

Developer specification должна быть достаточной для разработки без повторного
анализа source: цель, scope, non-goals, затронутые файлы/слои, expected behavior,
acceptance criteria, документация/swagger при необходимости, риски и вопросы.

Analyst brief должен кратко объяснять задачу, бизнес-контекст, текущее
состояние проекта и решение по scope.

Analyst memory должна фиксировать рабочее понимание: какие документы прочитаны,
какие части backend/frontend проверены, какие паттерны нужно повторить, какие
ограничения нельзя нарушать.

После этого:

1. Обнови `../../../../../history/tasks/<TASK_ID>/task.json -> artifacts`.
2. Обнови `experience.json`.
3. Если были расхождения в `backend/docs` или `frontend/docs`, сначала исправь
   документацию и зафиксируй это в brief/memory.
4. Добавь событие в `../../../../../history/tasks/<TASK_ID>/task.json -> events`.
5. Увеличь `runtime.revision` в `../../../../../history/tasks/<TASK_ID>/task.json`.
6. Переведи задачу в `architecture` через CLI:

```bash
harv move <TASK_ID> --to architecture --owner analyst
```

7. Проверь, что `runtime.current_stage = "architecture"`.
8. Проверь, что `runtime.status = "ready_for_next_stage"`.
9. Проверь, что задача удалена из `queue.json` и добавлена в
   `../3-architecture/queue.json`.

Перед финальной записью перечитай `../../../../../history/tasks/<TASK_ID>/task.json` и
остановись, если `runtime.revision`, `runtime.current_stage` или `runtime.lease`
изменились.

## Запреты

- Не реализуй код.
- Не придумывай требования на вырост.
- Не переводи задачу дальше без brief и specification.
- Не переводи задачу в `architecture`, если найденный drift в backend/frontend
  docs ещё не исправлен.


## Статус в `tasks.json`

`tasks/backlog/tasks.json -> tasks.<TASK_ID>` должен показывать текущие `current_stage`, `status`, `revision` и `runtime_updated_at`. При перемещении задачи используй `harv move`: CLI обновляет `task.json`, очереди и `tasks.json`. Если runtime меняется вручную, синхронизируй эти поля в `tasks.json` той же правкой.
